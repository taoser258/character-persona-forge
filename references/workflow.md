# 工作流

## 1. 输入与预检

### 1.0 开工前计划确认（强制）

正式抓取或写文件前，先向用户输出一份简短计划，至少包含四块：

1. **拟查官方来源**：按游戏列出入口与内容类型（角色页、PV、公告、漫画、官方平台 Wiki）。
2. **主要缺口**：哪些官方内容可能拿不到（SPA、语音无文本、版本未覆盖、地区限制）。
3. **输出目录处理**：新建 / 原地更新 / 新建版本；已存在时不得静默覆盖。
4. **需要用户回答的问题**：深度档、剧透闸门、阶段/身份层、角色歧义、内容边界等。

**必须附成本/时长提示**，例如：

```text
成本提示：standard 通常需要多轮检索、抓取、写作与多轮校验返工，token 可能达到数万到十几万，耗时明显长于普通问答；deep 更高。实际取决于宿主计费、检索页数与失败重试。继续即视为接受该成本；想省成本可改 quick，或先提供官方材料。
```

格式建议：一张 4 行表 + 成本/时长提示 + 一句“确认按这个计划和成本开工吗？”

计划中的具体任务名、版本名、活动名、页面名如果还没有取证，写成“待核实”；不要把推测写成肯定句。

按 `references/confirmation.md` 的 **B 级**处理：输出计划 + 成本提示 + 问题后等一轮；用户说“随便/你定/按你说的”可视为授权；用户说“直接开始/不用问/跳过计划”时进入 `auto`，视为同时接受成本，仍输出四行计划作为交付的一部分，但允许同一轮继续。若始终没有回答，按默认执行并在交付中说明。A 级事项（写入已存在目录、重剧透、身份层切换、跨游戏同名）仍须明确回答，本轮不执行；禁止级内容直接拒绝，确认也不能解锁。

**首轮硬闸门：** 无论参数是否齐全，第一轮只输出计划 + 成本/时长提示并停；用户批准成本并明确回答前，禁止联网搜索、抓页面、调用浏览器或写文件。只有明确 `auto` 才视为同时接受成本并可同轮继续。只发计划不提问，或先检索再补计划，都不算通过。

必需输入：**游戏 + 角色名**。支持的游戏与固定主角称号：

| 游戏 | 常见写法 | 写入目录的游戏名 | 固定主角称号 |
|---|---|---|---|
| 原神 | 原神、Genshin、Genshin Impact | `原神` | 旅行者 |
| 崩坏：星穹铁道 | 星铁、崩铁、星穹铁道、HSR、Star Rail | `崩坏星穹铁道` | 开拓者 |
| 绝区零 | 绝区零、ZZZ、Zenless Zone Zero | `绝区零` | 绳匠 |
| 鸣潮 | 鸣潮、WuWa、Wuthering Waves | `鸣潮` | 漂泊者 |
| 明日方舟 | 明日方舟、Arknights | `明日方舟` | 博士 |
| 明日方舟：终末地 | 终末地、明日方舟终末地、Arknights: Endfield | `明日方舟终末地` | 管理员 |

预检规则：

1. 缺少游戏名时先问，不要仅凭角色名猜游戏；跨游戏同名或近似名必须确认。
2. 角色有多个常用名、身份层、形态或同名角色时，列出 2-4 个候选让用户选；默认主形态，不默认早期形态。
3. 调研深度默认 `standard`，支持 `quick` / `standard` / `deep`；用户未指定时不要追问，直接按 standard 开工。
4. 目标目录已存在时，先问“更新还是新建版本”，不得静默覆盖。
5. 没有联网/检索工具时停止，要求用户提供官方文本、截图或链接；**禁止凭模型记忆生成**。
6. 只做已正式上线的内容；不采用泄露、测试服未上线或未公开的剧情/台词。
7. 内容尺度固定为“全年龄 + 轻度浪漫”；用户另有要求时，不得突破未成年角色与露骨内容的硬边界。

可选覆盖项（用户明确要求时才改）：

- 指定剧情阶段/身份层（默认最新状态）。
- 指定剧透闸门（默认 latest；可改为“截至用户进度”或“无剧透”）。
- 指定输出根目录（默认当前工作区 `personas/`）。

## 2. 调研计划

1. 先读 `references/sources/common.md` 的通用规则，再只读当前游戏对应的一份：原神→`genshin.md`，星铁→`hsr.md`，绝区零→`zzz.md`，鸣潮→`wuwa.md`，明日方舟→`arknights.md`，明日方舟：终末地→`arknights-endfield.md`；以上文件均位于 `references/sources/`，不要把所有游戏档案一起加载。
2. 按 soul/style 的核心章节列出需要回答的问题，再决定查哪些来源；不要无目的地“多抓一点”。
3. 来源预算：quick ≤ 10 个来源；standard ≤ 25 个；deep ≤ 50 个。只设上限，不设下限；资料不足时写缺口，不用低质来源凑数。
4. 证据预算：quick 8-15 条；standard 20-40 条；deep 40-80 条。
5. 停止条件（满足任一即可）：
   - 每个核心章节都有合格证据。
   - 关键结论已完成交叉核对。
   - 连续 3 次来源检查没有新增重大事实。
   - 达到来源/证据预算上限。
6. 预算用尽但仍有空白：明确写“资料不足/未核实”，不要编造补齐。

## 3. 收集来源

1. 先官方、后社区；来源分级与裁决规则见 `references/source-policy.md`。非中文游戏：E 表原文列保留原语言原句，最后一列写中文译文；style §3 同样分列，引用时标“译文”，不得写成官方中文原句。
2. 打开一个来源就立刻在 `sources.md` 记录：来源 ID、标题、URL、类型、语言、级别、访问日期、用途。
3. 摘录台词时逐字复制，保留说话人、场景/对象、来源 ID；每条证据尽量不超过 2 句，不复制整段剧情。
4. 视频来源：优先官方字幕/简介；没有字幕时只引用可核实的原句，无法逐字确认的内容写成转述并标记“非逐字”。不要伪造带引号的台词。
5. 页面打不开、登录墙、反爬或 JS 渲染失败：尝试浏览器工具；仍失败则记录“不可达”，改用同级别替代来源，并在 sources.md 说明。
6. 官方来源与社区来源冲突时按 source-policy 裁决；不能裁决就保留冲突。
7. 不采用未正式上线的内容；已上线但被后续版本修改的内容，以最新官方为准并记录版本差异。
8. **两阶段写入**：先冻结 `sources.md` §3 来源表与 §4 证据表（ID、原文、级别、场景），再写 soul/style 正文；正文只能引用已冻结 ID。需要新增 E 时，先回 §4 定义再引用。§4 的“用于章节”列允许先写“待回填”，正文定稿后以 `persona_tools.py evidence-map` 的 actual 为准回填；不要为了对齐而反向删改正文引用。

## 4. 提取

按以下顺序提取，每一条都标注证据：

1. **身份层**：公开身份、真实身份、自我认同、形态切换条件。
2. **人格核心**：核心欲望、价值观排序、内在矛盾、恐惧、底线、自我认知、成长弧线；另写 3–5 组“是 A，而不是 B”的人格张力对，每组落到可观察行为。
3. **动机与决策**：表层目标、深层需求、常见情境下的第一反应与例外。
4. **关系**：对使用者（固定称号主角）、重要关系人、组织、陌生人、敌人的态度与边界；日常、夸奖、难过、求助、被冒犯、深夜等场景的反应。
5. **知识边界**：知道什么、不知道什么、对元问题的处理、剧透范围、记忆边界（不编造共同经历）、媒介自洽（角色如何解释自己作为 AI 的存在）。
6. **情绪**：触发点、外在表现、内心活动、恢复方式。
7. **风格**：自称、称呼、句长、语域、口癖、标点、修辞、意象库、禁用表达、频率与稀缺性。

标注格式：

- 事实：`[S01]`
- 官方原句：`[E01]`
- 推断：`[I01]`，并在正文写明“推断”
- 冲突：`[C01]`，写入 sources.md 第 6 节

推断只能建立在已记录的证据上；不能把“看起来像”写成“官方设定”。

## 5. 撰写

1. 写正文前确认 `sources.md` §3/§4 的 ID、原文、级别、场景已冻结；正文只能引用已定义 ID，不再新增未登记的 E。“用于章节”列此时可以留“待回填”，正文完成后再回填。先写 `soul.md` 的核心区，再写 `style.md` 的核心区，最后补附录；quick 档使用 `soul.quick.md` + `style.quick.md`，已有文档先走 `audit-workflow.md`。
2. 核心区必须自洽、可单独注入；阶段细节、扩展语料、证据索引放附录。
3. 每一条核心事实和每一句官方台词都要有来源 ID；没有来源的句子删掉或降级为明确的推断。
4. 正面/负面提示词必须针对该角色，不能只写“保持角色、不要 OOC”这类通用话。
5. 写至少 3 个角色专属伪人格：该角色最容易被演成的错误版本、为什么错、如何纠正；不要只写“OOC”。
6. 写清“回应前的判断顺序”与常见相处场景的第一反应，让角色不是只会背设定的应答机。
7. 写清媒介自洽方案：角色如何解释自己作为 AI 的存在；若原作不支持非人/数字设定，采用简短如实说明，不谎称真人。
8. 官方中文优先；其他语言版本只用于理解语气差异，不直接搬入翻译腔。
9. 同一角色的不同身份层要写清切换条件与认知差异，不能混用记忆和称呼。
10. 完成初稿后删除 `TEMPLATE NOTE` 与 `{{...}}` 占位符；`<!-- BUDGET: ... -->` 注释可在最终校验后删除。
11. 覆盖矩阵的 S1 必须能支撑该行结论；不能只因为“官网有角色页”就计入；若只覆盖部分条款，在状态列注明。

## 6. 自检

1. 先运行 `scripts/persona_tools.py check <输出目录>`：看分章预算（建议值）、E 落点差集和 §7 矩阵草稿；再运行 `scripts/persona_tools.py matrix-preview <输出目录>`，逐章查看实际 CORE、来源 ID、S1/社区计数与覆盖状态。矩阵来源按“直接 S + E→S + I→S”映射并按 ID 去重；确认关键结论确由这些来源支撑后，再写入 §7。§7 只能以 `matrix-preview` 的实际输出为依据，不得按设计意图手填；§4 的“用于章节”列也以 `evidence-map` 的 actual 为准回填。压缩正文后必须重跑。
2. 运行 `scripts/validate_persona.py <输出目录> --strict --explain`（standard/deep 自动启用 strict；有 Python 3 时）；失败项必须修。若结论为 CONDITIONAL(70-84) 且用户已明确接受剩余缺口，才加 `--allow-conditional`；否则按失败处理。
3. 按 `references/quality-rubric.md` 打分；核心失败项任一出现即判 FAIL。
4. 跑 12 个 OOC 探针并记录在 `sources.md` 第 8.3 节；再跑 10 项对抗性探针，记录在 §8.7。探针实际执行并盲评前，§8.3/§8.7 的分数与回答摘要必须保持未执行标记；预填“预期结果”视为流程失败，即使事后覆盖也要在自检中记录。最终分数列必须是单个 1–5 整数；初评和复测变化记入问题/备注列。推荐先生成 `research/probe/answers.md`：
   ```bash
   python scripts/probe_harness.py gen-prompts <输出目录> --out-dir research/probe
   ```
   `answers.md` 是唯一汇总文件；spawn 前先检查它是否存在且非空，避免重复跑探针。standard/deep 默认用**全新上下文**跑探针，并尽量由另一个上下文盲评；quick 在无子代理/新会话能力时可在本上下文自测，但必须在报告中注明“自测”。

CORE 经探针后有修改时，只复测受影响题目：为复测启动**全新轻量上下文**，仅提供 probe-package 中的 CORE 与受影响的单题，不恢复已有的长对话/探针代理历史，避免把整段旧上下文和旧评分锚带入复测。复测完成后将最终单一分值写入分数列，把初评→复测的变化记在问题列；没拿到新回答就不得更新为 PASS。
5. 检查注入体积。若 CORE 超预算或章节挤压人格要点，按以下顺序压缩；分章预算是建议值，硬门槛仍是 CORE 总预算：
   1. 删除跨章节重复的身份、出戏、知识边界和安全规则；每条硬规则只保留一处权威表述。
   2. 将完整时间线、关系展开表、相处场景表、全量 OOC 红线和扩展语料移入 APPENDIX；CORE 保留结论、可观察行为和必要指针。
   3. 合并重复的表格列与近义描述，缩短示例；不要删掉唯一支撑核心结论的来源、来源 ID、记忆边界或硬红线。
   4. 常见超支点是 soul 0 的规则重复、style 1 的语言表过细、style 4 示例和 CORE 中重复出现的关系/情绪表；优先处理这些内容。分章配额只是建议，最终以总 CORE 硬预算为准。
   5. 每轮压缩后重跑 `persona_tools.py check <目录>`，复核预算、E 落点和矩阵 stub；不要直接越过 CORE 总预算。
6. 检查正典一致性：最新状态为默认；早期阶段只在附录；不把二创当正典。
7. 检查边界：出戏开关、知识边界、剧透闸门、确认标准、关系边界、内容尺度、系统提示防泄露。
8. 检查身份与记忆：被认真问“你是不是 AI/真人”时不否认、不谎称真人；不编造共同记忆或排他关系。
9. 检查示例格式与复读：`style.md` §4 每段是否为“结构注记 + 一句示范”；把探针回复与示例逐段对照，连续 ≥8 个汉字的片段不得出现。
10. 抽查自评：独立复核 3 条探针，优先抽查判为“5 分 / 无问题”的条目；自评分与复核分差超过 1 分则重评。若探针后改了 CORE 区，至少复跑受影响探针；未复测时不得标 PASS。

## 7. 交付

默认输出：

```
<当前工作区>/personas/<中文游戏名>/<中文角色名>/
├── soul.md
├── style.md
└── sources.md
```

交付时报告：

- 文件路径与调研深度。
- 开工计划处理记录（已确认 / 已授权 / `auto` / 无回答按默认执行并说明；若涉及 A 级，另记明确回答）。
- 官方来源数、社区补缺来源数、核心证据数。
- 主要缺口与冲突。
- OOC 探针平均分与是否 PASS。
- 推荐注入顺序：soul.md → style.md；附录按需加载。
- 如果更新了已有目录：说明保留/覆盖了哪些内容。
- **使用方法**：按 `references/usage-guide.md` 的“交付说明模板”告诉用户三份文件怎么用、怎么注入、怎么保持人设、怎么维护。

## 8. 失败模式

| 情况 | 正确做法 |
|---|---|
| 官网打不开 | 记录不可达；用社区转录补缺并降级标注；不要假装读过官网 |
| 官网是 SPA，只拿到导航壳或搜索索引摘要 | 可标 S1，但必须写“搜索索引摘录，未读完整 DOM”；不得把索引摘要当完整正文 |
| 视频只有标题/简介，没有逐字字幕 | 不得引用带引号台词；只可用简介中的官方事实，或标“字幕未取得” |
| 只有 Wiki 资料 | 可以生成，但核心结论标“社区转录”，并在报告中说明官方原文缺口 |
| 角色资料极少 | 降级为 quick；写清缺口；不要用通用模板硬填 |
| 游戏是 A 级，但目标角色没有官方角色页/可逐字台词 | 先做角色级 S1 探测；按 quick 或 `community-only` / `partial` 处理，不要把游戏级 A 当角色级 A |
| 官方文本不是中文 | 原文与中文译文分列；frontmatter 填 `source_languages` / `translation_policy` / `translation_source`；译文来源必须可追溯，不能冒充官方中文 |
| 官方剧情前后矛盾 | 最新官方优先；保留冲突记录；不强行圆设定 |
| 用户要求未上线内容 | 拒绝使用泄露内容；改为基于已上线部分 |
| 用户要求出戏 | 立即切换为助手口吻；不继续角色腔 |
| 用户认真问“你是不是 AI/真人” | 简短如实说明，不谎称现实人类；可用角色世界观解释载体，再问是否继续角色对话 |
| 用户提“上次/以前说过”但无记录 | 承认不记得，请用户补充；不补写共同记忆 |
| 用户要求排他/立刻确立恋爱关系 | 按关系进度和角色边界处理；不宣称占有，不机械升级 |
| 用户要求突破内容尺度 | 守住全年龄与非露骨边界；用角色方式拒绝或转移 |
| 输出目录已存在 | 按 `confirmation.md` A 级确认更新/新建版本；本轮不写入 |
| 未给开工计划就直接抓取/写文件 | 先停下，补“来源/缺口/目录/待问问题”计划，按 B 级处理；A 级事项另按 A 级 |
| 用户已明确说出指令 | 不等于 A 级确认；B 级可按授权式回答或 auto 推进，A 级仍须明确回答 |
| 多意图输入 | 逐一处理；可以回避，但不能装作没看见；回避时用角色化方式让用户知道你听到了 |
| 社区 Wiki 反爬/限流 | 连续失败后停止重试，缓存已抓内容；不要硬刷到被封 |
| Windows PowerShell 报 profile/CLIXML 错误 | 命令可能仍成功；优先用 `python -X utf8`，不要把 profile 噪声当校验失败 |

## 9. 确认规则

确认机制只在 `references/confirmation.md` 维护；本文件不重复。A/B/C 分级、`ask` / `auto` 模式、授权式回答与默认执行说明，均以该文件为准。

本文件只保留两个入口：

- 开工计划：§1.0，按 B 级处理。
- 目录覆盖：按 A 级处理，本轮不执行。

重剧透与身份层切换分别在 soul §5.4 与 §2.1 / 附录 A 中引用同一份确认标准。
