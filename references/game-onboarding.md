# 任意游戏接入

> 适用于六款 curated 游戏之外的任意游戏。目标不是“看到游戏名就开工”，而是先判断**能不能做、能做到什么深度**，再生成 provisional pack 与来源档案，最后进入人格文档流程。
> 机器字段见 `games/schema.md`；通用取证规则见 `sources/common.md`。

## 0. v1.7 边界

支持：

- 固定主角称号（如“天命人”“博士”）。
- `live_service`（持续更新，按版本快照）与 `complete`（已完结线性正典）。
- 官方中文，或官方只有非中文（E 表保存原文 + 中文翻译，引用时标记译文）。
- 有可检索的官方入口和/或社区 Wiki 转录。

暂不支持，遇到就停并说明：

- 可选主角、自定义名字、群像叙事（`selectable` / `custom` / `ensemble`）。
- 多路线、多结局、重制版、EA、沙盒（`branching` / `remake` / `early_access` / `sandbox`）。
- 没有任何可检索来源，且用户拒绝提供材料。
- 泄露、测试服、未正式上线内容。
- SillyTavern 角色卡/世界书导出（本轮不做）。

## 1. 先问用户（A 级）

| # | 问题 | 为什么必须问 |
|---|---|---|
| 1 | 游戏全称、常用简称、英文名 | 决定 pack 的 `display_name` / `aliases`，避免和已有游戏重名 |
| 2 | 官方语言；是否有官方中文 | 决定 `languages` 与翻译政策；非中文原文不能假装官方中文 |
| 3 | 玩家主角是固定称号、可选、自定义还是群像 | v1.7 只支持固定；其它模式要停，不能偷偷默认一个 |
| 4 | 正典状态：持续更新、已完结、多路线、重制、EA | 决定 `canon.type` 与版本快照方式；多路线/重制/EA 暂不支持 |
| 5 | 目标角色、形态/时期、剧透闸门 | 同名/多形态角色必须先消歧 |
| 6 | 内容分级与关系边界 | 默认全年龄 + 轻度浪漫；露骨或性化未成年角色直接拒绝 |
| 7 | 输出目录 | 默认 `personas/<pack.directory>/<角色名>/`，用户可改 |

来源地形**不要**直接问用户“是 A 还是 B”。先做第 2 步侦察，再给出定级建议让用户确认。

## 2. 来源发现（只侦察，不写人格）

对目标游戏做一轮轻量侦察，每类至少查一次，记录“可达/不可达、语言、是否有角色级内容”：

| 探测 | 要找什么 | 记录 |
|---|---|---|
| 官方站 | 官网、发行页、公告、角色页 | URL、语言、是否 SPA、角色页是否存在 |
| 官方社媒/视频 | 官方账号、PV、角色演示、版本公告 | 账号认证、作品归属、是否有可核实字幕 |
| 社区 Wiki | BWIKI / Fandom / 萌百 / 灰机等 | 角色页、语音页、剧情页、影神图/档案 |
| 搜索索引 | `site:` 检索、角色名 + 台词/语音/剧情 | 能否稳定命中角色级页面 |
| 可达性 | 登录墙、403、地区限制、反爬 | 不可达就记录，不硬刷、不假装读过 |
| 语言 | 官方原文语言、社区转录语言 | 非中文原文是否有人工翻译 |

输出一张“来源地形证据表”，不要在这一步写 `soul.md` / `style.md`，也不要凭模型记忆补角色设定。

## 3. 定级 A/B/C/D/E

| 等级 | 判定 | v1.7 承诺 |
|---|---|---|
| `A` | 官方中文入口（角色/公告/影像至少一类）+ 社区 Wiki 能覆盖目标角色 | standard / deep |
| `B` | 官方只有非中文，或官方页面很少；社区 Wiki 能覆盖 | standard，按翻译政策标译文 |
| `C` | 有官方入口，但社区 Wiki 对目标角色覆盖不足 | standard，章节如实标 `community-only` / `derived` |
| `D` | 只有社区 Wiki/二创，官方不可达 | 仅 quick，默认 CONDITIONAL，需用户显式接受 |
| `E` | 没有任何可检索来源 | 拒绝生成 |

定级是**人工判断**，不是脚本自动检测。判不准时按更保守的一档处理，并在 `source_landscape_notes` 写清理由。

### 3.1 角色级 S1 探测（不要只看游戏级）

**游戏是 A/B/C，不代表目标角色有 S1。** 写 pack 后、开工前，对目标角色再做五项探测：

1. 官网/发行页是否有该角色的官方档案或官方介绍。
2. 官方 PV/演示/公告中是否有该角色可逐字核实的台词。
3. 官方设定集、访谈、社媒是否有该角色的正式资料。
4. 社区 Wiki 是否有角色页、语音页、影神图/档案转录。
5. 社区转录能否找到第二个独立来源交叉。

| 游戏级 | 角色级 S1 | 允许深度 | 处理 |
|---|---|---|---|
| A/B | ≥1 | standard / deep | 正常按档位做 |
| A/B | 0 | quick，或 standard 但如实标 `partial` / `community-only` / `derived` | 官方优先项会扣分；standard 需用户接受较低官方覆盖 |
| C | ≥1 | standard | 其余章节按社区补缺标注 |
| C/D | 0 | quick | 默认 CONDITIONAL，需用户显式接受 |
| 任意 | 无角色页且无社区转录 | 拒绝 | 要求用户提供官方材料 |

黑神话试点就是第一种反例：游戏级 A，但官网只有营销页，二郎神角色级 S1=0；最终 quick 档 86 分，14 个核心章节里 12 个标 `community-only` / `derived`，官方优先仅 8/15。**不要为了凑 A 级硬把官网首页或关卡名写成角色级 S1。**

角色级探测结果写进开工计划的“来源/缺口”两行；如果结论是 quick 或 CONDITIONAL，必须先告诉用户，再开工。

## 4. 创建 provisional pack

```bash
python scripts/game_profile.py init \
  --id black-myth-wukong \
  --display-name "黑神话：悟空" \
  --title "天命人" \
  --alias "黑神话悟空" \
  --alias "Black Myth: Wukong" \
  --game-field "黑神话悟空" \
  --landscape A \
  --canon complete
```

`init` 会：

1. 创建 `references/games/<id>.json`（`status=provisional`）。
2. 创建 `references/sources/<id>.md` 骨架，正文带 `TODO(接入待补)`。
3. 把 `id` 加进 `references/games/index.json`。
4. 拒绝与已有游戏冲突的别名、`game_field`、`directory`。

约定：

- `id` 只能是小写字母/数字/连字符，且与文件名一致。
- `alias` 全局唯一（大小写不敏感）；展示名会自动加入。
- `directory` 是单层安全目录名，默认由展示名去标点得到。
- `--force` 只允许覆盖 `provisional` 档案，不会覆盖已写好的来源档案。
- `--landscape D` 会自动把默认深度压到 `quick`；`E` 仍可建骨架，但 `game-check` 会拒绝。

## 5. 补全来源档案

按骨架逐节填写，至少包括：

- 官方入口：名称、URL、内容类型、语言、访问/抽取备注、核实状态。
- 官方可直接取得：哪些事实/台词能直接读到。
- 官方缺口：哪些角色档案、语音、剧情只能靠社区转录。
- 检索式：官方域名、社区 Wiki、角色名 + 台词/语音/剧情。
- 社区补缺：强项、页面标题规律、已知错漏。
- 抽取顺序与边界：先官方、再社区、再交叉核对。
- 已知取证陷阱：SPA、账号改名、系列混用、攻略站编造、剧透。
- 维护记录：日期、变更、核实人。

要求：

- 引用分级用 `source-policy.md` 的 S1–S4；社区转录标 S3。
- 非中文原文：按 `games/schema.md` §6 在 E 表最后一列写中文译文，frontmatter 填 `source_languages` / `translation_policy` / `translation_source`；不得把社区译文说成官方中文。
- 每条来源记录 URL、标题、语言、访问日期；不可达也记录。
- 攻略站只用于定位场景，不单独支撑人格结论。
- 同一 IP 的续作、DLC、联动分开建档，不共享记忆。

## 6. 校验与用户确认

```bash
python scripts/game_profile.py game-check <id>
python scripts/game_profile.py check
python scripts/selftest.py
```

`game-check` 的四种状态：

| 状态 | 退出码 | 含义 | 下一步 |
|---|---:|---|---|
| `READY` | 0 | 档案有效、来源档案无 TODO、深度未超限 | 给用户确认后进入人格流程 |
| `INCOMPLETE` | 2 | 来源档案还有 TODO | 补完再查 |
| `CONDITIONAL` | 2 | 来源地形 D | 用户明确接受后加 `--accept-conditional` |
| `FAIL` | 1 | 字段错误、E 级、深度超限、语言政策矛盾等 | 按错误修复 |

用户确认以下内容后，把 `status` 从 `provisional` 改为 `curated`：

- 展示名与别名；
- 固定主角称号；
- 来源地形与最高深度；
- 正典类型与版本快照；
- 目标角色是否在覆盖范围内。

`provisional` 不是“不能做”，而是“接入信息还没被用户确认”。带 provisional 开工必须在计划里明确说明。

## 7. 进入人格文档

`game-check` 为 `READY` 后，按 `SKILL.md` 的流程走：

1. 首轮仍只输出四行开工计划 + 成本/时长提示，等用户确认。
2. 来源阶段读 `sources/common.md` + 本游戏的 `sources/<id>.md`。
3. 用 pack 里的 `default_title` 作为玩家称号，`directory` 作为默认目录。
4. 覆盖率不足的章节如实标 `community-only` / `derived`，不用攻略站或模型记忆硬补。

## 8. 常见失败模式

- **把游戏级 A 当角色级 A**：官网存在不等于目标角色有官方角色页；必须先做 §3.1 的角色级 S1 探测。
- **官网只是营销页**：能读到世界观标语，但没有角色详情；不要把首页文案当成角色级 S1。
- **官方账号系列化**：账号改名后同时发续作内容；按作品、日期和标签过滤，不把续作设定写进本作。
- **Wiki 页面标题与常用名不同**：先查重定向/消歧页，别因为搜不到常用名就判定“没有资料”。
- **攻略站错漏/编造**：数值、解锁条件、皮肤等说法可能互相矛盾；只取能被 Wiki 或官方影像交叉的内容。
- **语音合集混场景**：序章、Boss 阶段、隐藏结局、变身彩蛋可能被拼成一条；引用时标场景/阶段。
- **同人设定混入**：萌百/二创的 CP、昵称、推测不能进 soul/style；只作交叉核对线索。
- **剧透失控**：隐藏结局、真结局、后期身份默认按用户闸门处理。
- **没有来源**：直接停，要求用户提供官方文本/截图/链接；不得凭记忆生成。

## 9. 维护

- `live_service`：新版本更新 `version_snapshot`，补来源与冲突记录。
- `complete`：补丁/DLC 若改变文本，记录版本与日期；不要把续作内容并入本作。
- 来源档案变更后重跑 `game-check`、`check`、`selftest.py`。
