# 审计与更新工作流

> 用于“已有角色文档”的补来源、修 OOC、更新剧情阶段或版本迁移。
> 从零创建走 `workflow.md`；本文件只处理已有文档。

## 1. 清点

1. 读取现有 `soul.md` / `style.md` / `sources.md`，确认 `version_snapshot`、`research_date`、`forge_version`。
2. 抽取 soul/style 中的事实句与台词，逐条映射到现有的 `[Sxx]`/`[Exx]`/`[Ixx]`/`[Cxx]`。
3. 列出三类问题：
   - 无来源句；
   - 引用 ID 断链；
   - 章节引用指错（如 `soul 4.6` 不存在）。
4. 运行 `python3 scripts/validate_persona.py <目录> --strict`，把输出作为审计基线。

## 2. 复核

1. 按 `sources.md` 的访问日期重验 URL，标出失效/改版来源。
2. 对照最新官方版本，列出：
   - 新增剧情/活动/语音；
   - 已改写或下线的旧文本；
   - 身份层、关系、知识边界的变化。
3. 对每条变化标剧透等级，决定进核心区还是附录 A。
4. 新来源按 `source-policy.md` 分级；不可达就写“不可达”，不补记忆。

## 3. 重打分

1. 只对受影响的章节重跑 OOC 探针，不整份重跑；若更新涉及运行时行为、身份或边界，同时重跑 10 项对抗性探针并更新 §8.7。
2. 每条探针先做“规则回查”（`quality-rubric.md` §6.1），再按 1–5 打分。
3. 记录旧分 → 新分：总分变化写入 `sources.md` §8.6，OOC 探针分数变化写入 §8.3，章节级变化写入审计报告，对抗性探针变化写入 §8.7；§9 只记版本/日期/变更/来源。
4. 若总分跨过 PASS/CONDITIONAL/FAIL 边界，按 `SKILL.md` / `quality-rubric.md` 的交付门槛与 `confirmation.md` 的确认规则处理。

## 4. 变更

1. 旧版本/旧日期/变更来源保留到 `sources.md` 第 9 节；旧分数保留到审计报告或 §8.6 备注。
2. 只改必要章节；不整份重写，除非结构本身需要升级。
3. 身份层/阶段变化只进附录 A，默认人格仍取最新官方状态。
4. 更新 `sources.md` 的冲突表与覆盖矩阵；新行按实际章节来源计数。
5. 若引用配额（style §3 ≤30 条/1,200 字；sources §4 ≤80 条/3,000 字）超限，先删氛围摘录。

## 5. 回写与验收

1. 更新 frontmatter：`version_snapshot`、`research_date`、`forge_version`。
2. 重跑 `python3 scripts/validate_persona.py <目录> --strict`，必须 PASS 或按交付门槛标 CONDITIONAL。
3. 抽 3 条自评做外部复核，自评分与复核分差 ≤1。
4. 在交付报告中列出：
   - 保留/覆盖了哪些章节；
   - 新增/失效来源；
   - 探针分数变化；
   - 仍未解决的缺口。

## 审计检查表

| 检查 | 通过标准 |
|---|---|
| 清点 | 所有核心事实有 S/E/I 编号；无来源句已列出 |
| 复核 | 每个失效来源有替代或“不可达”标注 |
| 重打分 | 受影响章节有旧分/新分记录；涉及运行时行为时，§8.7 已重跑并更新 |
| 变更 | 旧值保留；身份层未混用；矩阵计数与实际一致 |
| 回写 | `--strict` PASS 或 CONDITIONAL 经用户接受 |
| 报告 | 保留/覆盖、来源变化、分数变化、缺口四项齐全 |
